All colors and sizes above are **current code values**, not measurements of the user's monitor or sign-off targets. `scripts/ui_review.py` computes actual measured rectangles and WCAG contrast for specified small-text foreground/background pairs, fails on missing screenshots, off-client panels, wrong selected/protected states or background rejection, and writes `review.json` with `approved_reference: false`. It now also rejects a **physical client size different from the requested size** and (for new captures with Win32 monitor metadata) a client/popup outside the monitor working area. Existing captures can be re-audited for size, but older folders lack monitor/button metadata or the newly measured scrollable-panel viewport. Reports expose `screen_fit_verified`, `header_actions_verified`, and `panel_viewport_verified` separately; an unknown viewport does not count as a successful on-screen panel check. For scale-specific evidence, capture with `python scripts/capture_editor_baseline.py --window 1000x700 --expected-dpi 144 --output <new-folder>` at 150%; it aborts **before screenshots** if the new editor window reports the wrong effective DPI. Review with `python scripts/ui_review.py <folder> --expected-dpi 144`. Use 96 for 100% and 120 for 125%; the recorded window DPI is printed even without a requirement. A folder named `review-125` is not a 125% test if its effective window DPI is 96. It does not grade the look of text, focus indication, keyboard traversal, font rasterization or closeness to the AI concept. The GitHub-hosted Windows runner only exposes a 1024×720 work area; CI therefore requests 960×640 and 980×650 **runner-fitting smoke captures**, not the user's 1456×766 reference or high-DPI validation. If either does not actually fit, the audit must fail.

## Responsive behavior and manual matrix

The editor uses weighted center grid (`sidebar` fixed request, `workspace` expands, `panel` fixed request) and a scrollable adjustment column. Tk's launch-time minimum is requested as 960×640 **physical** pixels rather than 960×640 CTk logical units; this prevents an automatic 150% multiplication of the minimum. It does **not** establish that every scaled control fits in 1000×700, that a popup's contents fit, or that a monitor's usable area accommodates the outer window. The header stacks its two action groups when they cannot both fit on one row and omits its redundant brand text below 1100 physical pixels; the audit checks button bounds on new captures. The canvas has a small requested minimum instead of Tk's large default, and the Before/After control moves from the footer to the scrollable adjustment rail on cramped clients. Popups center using physical sizes and clamp to the monitor work area where possible; the export shade now uses unscaled physical editor bounds. None of this proves every control or popup is usable at real 125%/150%—a fresh high-DPI capture and human inspection are still required. Test the same selected photo and modal at (1) primary 1456×766 100%, (2) narrow 1000×700 100%, (3) 125%, (4) 150%, and (5) largest usable viewport, recording *actual* DPI, OS text scaling, display resolution and window bounds. Any physical clipping, hidden button, absent focus ring, unreadable text or popup outside the visible monitor is a failure, not a tolerance adjustment.

For primary major edges, ±2–4 **physical** pixels is only a **proposed** starting tolerance. Approve named ROIs/masks and final tolerances against real Windows 11 captures, not against the generated sample camera or the illustrated concept. Windows ClearType/font antialiasing is reviewed separately; do not treat a literal full-frame pixel mismatch as a UI failure when it is limited to rasterization. Real user photos and screenshot filenames can be private; keep them in ignored `ui-captures/` and share only reviewed artifacts.

Once the user actually approves a Windows 11 reference package, save a **local**, ignored `review-manifest.json` beside its `capture.json` and screenshots, with `approved: true`, `scope: "chrome-only"`, `approved_by`, `approved_at`, `reference_id`, and an explicitly reviewed `regions` object. Each state maps to ROI objects with `name`, `rect: [x,y,width,height]`, `exclude` (for variable text), `channel_delta` and `max_changed_fraction`. Run `python scripts/compare_ui_capture.py --manifest <reference>/review-manifest.json --actual <new-capture> --output ui-captures/diff`. This tool refuses missing/unapproved manifests, mismatched viewport/DPI or out-of-bounds ROIs and writes `comparison.json` plus red-only diff masks; it never compares the whole sample photograph by default. The manifest is **not cryptographic approval**—a human must approve it and inspect the visual artifacts. CI does not pretend its generated fixture is an approved golden baseline. MUH-44 and MUH-53 remain open until the human-approved reference and multi-DPI checks exist.
