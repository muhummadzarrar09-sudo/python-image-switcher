# Editor performance work — alpha.7 (MUH-55 / MUH-56)

## What is now faster

- The canvas preview decodes only up to the visible canvas size (JPEG decoder draft when applicable). A 100% source view is **not** claimed; full-resolution master export still decodes/renders the original.
- Sliders debounce by 75 ms, then a single background worker coalesces pending renders. Old results cannot overwrite a newer photo/setting/size. Only Pillow/NumPy work happens on that worker; `ImageTk.PhotoImage`, status and canvas changes remain on Tk's UI thread. The worker has one pending request and one completed image at most.
- Alpha.6 keeps **at most 48 numbered thumbnail tiles** mounted in the rail, with explicit previous/next pages while all photos and protected edits remain in the batch. It decodes rail images at thumbnail size; changing pages may need to decode again after eviction from the **192-image LRU**. Import queues at most 24 decoded-file results ahead of the UI, rather than retaining hundreds of pending Pillow images. This bounds widget and pending-decode memory but is not a measured 400+ real-photo guarantee; profiling pagination, queue throughput and peak RSS remains part of MUH-55.
- Unedited full-resolution renders skip RGB float conversion entirely; adjusted renders reuse float buffers for quantization and Sharpness. Untouched originals and `.isphoto` files are unchanged. Pixel hashes for the four tested 8-bit JPEG recipes (default, exposure/contrast, Sharpness, mixed controls) matched the pre-change implementation; other cameras/RAW require verification.

## GPU: automatic at app startup and guarded batch color math, not full-editor acceleration

The user's Windows 11 report: **15.7 GiB RAM**, Intel Iris Xe (`32.0.101.6790`) and RTX 4070 Laptop (`32.0.16.1692`). WMI-reported 2/4 GiB adapter RAM was inaccurate for the RTX: OpenCL on the actual laptop reports **8 GiB**, driver `616.92`. The user's generated-pixel 2400×1600 OpenCL exposure+contrast probe measured CPU **0.08767 s** versus GPU transfer+kernel+readback **0.00275 s**, with **0 differing channels out of 11,520,000**. That ~32× *isolated math* result is not a prediction for full UI speed, RAW decode or export. PyOpenCL emitted a non-fatal compiler-output warning; repeated-kernel-retrieval overhead in the probe has been fixed.

Alpha.7 **starts GPU capability detection at boot in a background thread**; Tk and CPU previews are not blocked while an OpenCL context compiles. The Windows updater best-effort installs the optional pyopencl wheel and the packaged editor bundles it if available; a missing wheel, ICD, GPU or driver failure leaves the app running on CPU. `IMAGE_SWITCHER_GPU=off` is an explicit troubleshooting override. The numbered rail shows `GPU ready: …`, `checking`, or `CPU fallback`, while the selected image says `experimental GPU` **only when that render used it**. The GPU handles canvas-size, 8-bit RGB **exposure and/or contrast only**. Sharpness, backgrounds, crop/rotation, alpha, NEF and unsupported settings run on CPU. In alpha.7, a batch export of 8-bit **RGB exposure/contrast-only** photos may also run its **full-resolution color math on the GPU** (not just the selected preview). Before the first master for each recipe, it checks **all 256 possible 8-bit channel inputs** for exact CPU/GPU equality; a mismatch or device failure re-renders the entire photo on CPU, never a partial GPU result. Unsupported recipes use CPU directly. The worker processes one photo at a time and copies GPU data in 1-million-pixel tiles to bound VRAM; original bytes, protected numbers, ICC and portable projects use the established paths. PNG/TIFF encoding, NEF/16-bit processing, Sharpness and other controls stay CPU. The user has now verified that the **installed alpha.7** used the RTX 4070 for one generated 2400×1600 numbered lossless master and its preview: `packaged: true`, `gpu_used_for_generated_export: true`, photo `#1`, CPU-vs-GPU full-render and exported PNG maximum channel difference **0**, no reported GPU error. This verifies the tested recipe and multiple GPU transfer tiles, not 400 distinct camera photos, all recipes, NEF or real-export throughput. MUH-56 stays open for varied settings/formats, failure-path and wider-device validation.

### Original isolated real-device kernel probe (different from integrated preview)

On the user's Windows machine, in this branch after pulling, install the **optional diagnostic-only** dependency into the existing ignored editor venv, then run the generated-pixel benchmark:

```powershell
.\.venv\Scripts\python.exe -m pip install "pyopencl==2026.1.4"
.\.venv\Scripts\python.exe scripts\probe_gpu.py --size 2400x1600
```

This runs a representative exposure+contrast OpenCL kernel on a GPU device (prefer NVIDIA, otherwise another OpenCL GPU; never silently label an OpenCL CPU as accelerated), compares channel-by-channel against the editor's current CPU arithmetic on *generated* RGB pixels, and reports median **host-transfer + kernel + readback** time, kernel-only time, CPU time, output differences and device-reported memory. Nothing is enabled in preview/export by installing the probe; if OpenCL is unavailable or the driver fails it prints `gpu_executed: false` and the editor still runs CPU-only. It does not read photos, print paths, or upload results. The user already ran this and the integrated source-preview probe, with results above. The **installed executable's generated `--gpu-report`** described in `BUILD.md` has since passed on the RTX for its one eligible recipe; next gates are timed full-file exports and varied-format/recipe tests. A successful isolated kernel probe by itself is **not** 16-bit NEF/ICC/Sharpness parity or packaged Windows compatibility. Do not mark MUH-56 complete until the optional backend and CPU fallback pass integrated hardware checks and full-fidelity comparisons.
